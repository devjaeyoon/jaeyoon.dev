# tl;dr

&nbsp;기존 Gatsby 기반 JavaScript 블로그에서 타입 정보가 없어 느꼈던 불편함을 해결하고자 TypeScript를 점진적으로 도입했다. 핵심 타입부터 정의하고 GraphQL 쿼리·외부 라이브러리·컴포넌트 props로 범위를 넓혀갔다. **데이터 구조를 코드로 확인하고, 잘못된 필드 접근이나 props 전달을 실행 전에 찾을 수 있게 된 것**이 가장 큰 변화였다.

# 지난 이야기

&nbsp;블로그 제작 과정에서 Gatsby를 선택하고, Lighthouse를 활용해 개선 지점을 살펴보았습니다. 하지만 개발을 진행하면서 한 가지 아쉬운 점이 있었습니다.

```javascript
// JavaScript로 작성된 기존 코드 예시
export default function Layout({ children }) {
  return (
    <>
      <Header />
      <Box
        as="main"
        width="calc(100vw - 20px)"
        maxWidth="1024px"
        margin="0 auto"
        wordBreak="keep-all"
      >
        {children}
      </Box>
      <Footer />
    </>
  );
}
```

&nbsp;바로 **타입 안정성의 부족**이었습니다. JavaScript의 동적 타이핑 특성상 런타임에 예상치 못한 오류가 발생하거나, IDE의 자동완성 기능이 제한적이었습니다. 특히 Gatsby의 GraphQL 쿼리 결과나 컴포넌트 props에 대한 타입 정보가 없어 개발 과정에서 불편함을 느꼈습니다.

# TypeScript 마이그레이션을 결정한 이유

## 1. 타입 안정성 확보

&nbsp;JavaScript는 동적 타이핑 언어로, 변수의 타입이 런타임에 결정됩니다. 이는 개발의 유연성을 제공하지만, 동시에 예상치 못한 오류의 원인이 되기도 합니다.

```javascript
// JavaScript - 런타임에 오류 발생 가능
function getPostTitle(post) {
  return post.frontmatter.title; // post가 undefined일 수 있음
}
```

&nbsp;TypeScript에서는 `post`가 없을 가능성을 `Post | undefined`로 표현할 수 있습니다. `strictNullChecks`를 켜두면 **값이 있는지 확인한 뒤 사용하도록** 타입 검사 단계에서 알려줍니다.

```typescript
// TypeScript - 컴파일 타임에 오류 감지
interface Post {
  frontmatter: {
    title: string;
    date: string;
  };
}

function getPostTitle(post: Post | undefined): string {
  if (!post) {
    return '제목 없음';
  }
  return post.frontmatter.title;
}
```

&nbsp;위 코드에서 `if` 검사를 없애면 `post`가 `undefined`일 수 있다는 오류가 납니다. 다만 [타입 정보는 JavaScript로 변환할 때 사라지기 때문에](https://www.typescriptlang.org/docs/handbook/2/basic-types.html#erased-types), API 응답처럼 외부에서 들어오는 데이터는 실행 시점에 따로 검증해야 합니다.

## 2. 개발자 경험 향상

&nbsp; TypeScript의 가장 큰 장점 중 하나는 **향상된 IDE 지원**입니다. 자동완성, 리팩토링, 오류 감지 등의 기능이 JavaScript 대비 훨씬 강력해집니다.
&nbsp;특히 Gatsby의 GraphQL 쿼리 결과에 대한 타입 정보를 제공받을 수 있어, 데이터 구조를 명확히 파악하고 안전하게 사용할 수 있습니다.

## 3. 코드 품질 향상

&nbsp;TypeScript는 코드의 의도를 명확히 표현할 수 있게 해줍니다. 함수의 매개변수와 반환값, 객체의 구조 등을 타입으로 정의함으로써 코드의 가독성과 유지보수성이 크게 향상됩니다.

# 마이그레이션 전략

## 1. 점진적 마이그레이션 접근

&nbsp;대규모 프로젝트를 한 번에 TypeScript로 변환하는 것은 위험할 수 있습니다. 따라서 **점진적 마이그레이션** 전략을 채택했습니다.

### 단계별 마이그레이션 계획

1. **TypeScript 설정 및 의존성 추가**
2. **타입 정의 파일 생성**
3. **Gatsby 설정 파일 변환**
4. **공통 컴포넌트 변환**
5. **페이지 및 템플릿 변환**
6. **유틸리티 함수 변환**

## 2. 타입 정의 우선 설계

&nbsp;마이그레이션을 시작하기 전에 프로젝트의 핵심 타입들을 먼저 정의했습니다.

```typescript
// src/types/index.ts
import type { IGatsbyImageData } from 'gatsby-plugin-image';

export interface SiteMetadata {
  title: string;
  description: string;
  siteUrl: string;
  author: string;
  image: string;
  trackingId: string;
  configs: {
    countOfInitialPost: number;
  };
  social: {
    github: string;
    email: string;
  };
}

export interface MdxNode {
  id: string;
  frontmatter: {
    title: string;
    date?: string;
    createdAt?: string;
    updatedAt?: string;
    category: string;
    slug?: string;
    description?: string;
    tags?: string[];
    tag?: string;
    thumbnail?: {
      childImageSharp: {
        gatsbyImageData: IGatsbyImageData;
      };
    };
    recommended?: boolean;
    development?: boolean;
  };
  // ... 기타 필드들
}
```

&nbsp;이렇게 핵심 타입을 정리해두면 **여러 컴포넌트에서 같은 데이터 구조를 공유**하고, IDE의 자동완성도 활용할 수 있습니다. 이미지 데이터에는 `gatsby-plugin-image`가 제공하는 `IGatsbyImageData` 타입을 사용할 수 있습니다.

# 마이그레이션 과정에서의 도전과 해결

## 1. Gatsby GraphQL 타입 문제

&nbsp;Gatsby의 GraphQL 쿼리 결과에 대한 타입 정의가 가장 큰 도전이었습니다. Gatsby는 자동으로 GraphQL 스키마를 생성하지만, 이를 TypeScript에서 활용하기 위해서는 추가적인 작업이 필요했습니다.

### 해결 방법

```typescript
// 페이지 컴포넌트에서 타입 정의
interface IndexPageData {
  allMdx: {
    nodes: MdxNode[];
  };
  recommendedPosts: {
    nodes: MdxNode[];
  };
  developmentPosts: {
    nodes: MdxNode[];
  };
}

export default function IndexPage({ data }: PageProps<IndexPageData>) {
  // 타입 안전한 데이터 사용
  const posts = data.allMdx.nodes;
  return <Layout>{/* 컴포넌트 렌더링 */}</Layout>;
}
```

## 2. 외부 라이브러리 타입 정의

&nbsp;외부 라이브러리를 사용할 때는 **가져오는 경로에 맞는 타입 선언**도 필요했습니다. 패키지에 포함된 타입이나 `@types` 패키지를 확인하고, 사용하는 경로의 선언이 없다면 직접 작성할 수 있습니다. 아래는 `smooth-scroll`의 배포 파일을 가져올 때 사용하는 선언 예시입니다.

### 해결 방법

```typescript
// src/types/modules.d.ts
declare module 'smooth-scroll/dist/smooth-scroll.min' {
  interface SmoothScrollOptions {
    speed?: number;
    speedAsDuration?: boolean;
    easing?: string;
    offset?: number;
    header?: string;
    topOnEmptyHash?: boolean;
    updateURL?: boolean;
    popstate?: boolean;
  }

  export default class SmoothScroll {
    constructor(selector: string, options?: SmoothScrollOptions);
    animateScroll(anchor: number | Element, toggle?: Element, options?: SmoothScrollOptions): void;
    destroy(): void;
  }
}
```

## 3. 컴포넌트 Props 타입 정의

&nbsp;React 컴포넌트의 props에 대한 타입 정의도 중요한 작업이었습니다. 특히 재사용 가능한 컴포넌트들의 props를 명확히 정의해야 했습니다.

```typescript
// 컴포넌트 Props 타입 정의
interface PostTitleProps {
  post: MdxNode;
}

interface PostContentProps {
  content: React.ReactNode;
}

interface LayoutProps {
  children: React.ReactNode;
  location?: Location;
}
```

# 마이그레이션 결과

## 1. 타입 안정성 확보

&nbsp;GraphQL 쿼리 결과와 컴포넌트 props에 타입을 적용해, 선언에 없는 필드 접근이나 잘못된 타입의 props 전달을 검사할 수 있게 됐습니다. 수동으로 작성한 GraphQL 타입은 쿼리가 바뀔 때 함께 갱신해야 합니다.

## 2. 개발 생산성 향상

&nbsp;IDE의 자동완성 기능이 크게 향상되어 개발 속도가 빨라졌습니다. 또한 리팩토링 시 관련된 모든 파일을 자동으로 찾아주는 기능도 매우 유용했습니다.

## 3. 코드 품질 향상

&nbsp;타입 정의를 통해 **컴포넌트가 어떤 값을 받고 반환하는지** 확인하기 쉬워졌습니다. 나중에 코드를 다시 읽을 때도 데이터 구조를 파악하는 데 도움이 되었습니다.

# 마이그레이션 과정에서 배운 점

## 1. 점진적 접근의 중요성

&nbsp;대규모 프로젝트의 마이그레이션은 한 번에 모든 것을 바꾸려 하지 말고, 단계별로 진행하는 것이 중요합니다. 이를 통해 각 단계에서 발생할 수 있는 문제를 빠르게 파악하고 해결할 수 있었습니다.

## 2. 타입 정의의 전략적 설계

&nbsp;프로젝트 초기에 핵심 타입들을 잘 정의하는 것이 중요합니다. 이는 마이그레이션 과정에서 일관성을 유지하고, 향후 유지보수에도 큰 도움이 됩니다.

## 3. 외부 라이브러리 대응

&nbsp;TypeScript 생태계가 성숙해졌다고 해도, 모든 라이브러리가 완벽한 타입 정의를 제공하지는 않습니다. 이에 대한 대응 방안을 미리 준비하는 것이 중요합니다.

# TypeScript와 개발 도구 설정

## 1. TypeScript 설정

&nbsp;점진적으로 옮길 수 있도록 `allowJs`로 JavaScript 파일을 함께 사용하고, `strict`로 엄격한 타입 검사를 켰습니다. JavaScript 출력은 빌드 도구에 맡기기 위해 `noEmit`을 사용했습니다. `skipLibCheck`는 선언 파일 검사를 생략하는 옵션으로, 검사 시간을 줄일 수 있는 대신 선언 파일 내부의 오류는 확인하지 않게 됩니다.

```json
// tsconfig.json
{
  "compilerOptions": {
    "target": "ES2020",
    "lib": ["dom", "dom.iterable", "es6"],
    "allowJs": true,
    "skipLibCheck": true,
    "esModuleInterop": true,
    "allowSyntheticDefaultImports": true,
    "strict": true,
    "forceConsistentCasingInFileNames": true,
    "module": "esnext",
    "moduleResolution": "node",
    "resolveJsonModule": true,
    "isolatedModules": true,
    "noEmit": true,
    "jsx": "react-jsx"
  }
}
```

## 2. ESLint TypeScript 통합

&nbsp;TypeScript와 ESLint를 통합하여 코드 품질을 더욱 향상시켰습니다.

# 마이그레이션 후 개선사항

## 1. 개발자 경험 향상

&nbsp;TypeScript 도입으로 인한 가장 큰 변화는 **개발자 경험의 향상**이었습니다. IDE의 자동완성, 오류 감지, 리팩토링 기능이 JavaScript 대비 훨씬 강력해졌습니다.

## 2. 코드 안정성 확보

&nbsp;잘못된 필드에 접근하거나 props를 다른 타입으로 전달하는 실수를 **코드를 실행하기 전에 확인할 수 있게 되었습니다.** 특히 여러 컴포넌트에서 함께 사용하는 타입을 수정할 때, 영향을 받는 부분을 찾기 편했습니다.

## 3. 유지보수성 향상

&nbsp;타입 정의를 통해 코드의 의도가 명확해지고, 새로운 기능 추가나 기존 코드 수정 시 더 안전하고 효율적으로 작업할 수 있게 되었습니다.

# 마치며

&nbsp;JavaScript에서 TypeScript로의 마이그레이션은 단순한 기술적 변화를 넘어서, **코드 품질과 개발자 경험을 크게 향상시키는 전략적 결정**이었습니다. 

&nbsp;특히 Gatsby와 같은 복잡한 프레임워크를 사용하는 프로젝트에서는 TypeScript의 타입 시스템이 제공하는 안정성이 더욱 빛을 발합니다. GraphQL 쿼리 결과의 타입 안정성, 컴포넌트 props의 명확한 정의, 그리고 IDE의 강력한 지원은 개발 과정을 크게 개선시켜주었습니다.

&nbsp;물론 마이그레이션 과정에서 어려움도 있었지만, 그 과정에서 배운 것들과 결과적으로 얻은 이익을 고려하면 충분히 가치 있는 투자였다고 생각합니다. 

&nbsp;앞으로도 TypeScript의 강력한 타입 시스템을 활용하여 더 안정적이고 유지보수하기 쉬운 코드를 작성해 나가고 싶습니다. **지금까지 긴 글 읽어주셔서 감사합니다!**
